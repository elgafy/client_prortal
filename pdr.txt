# Client Projects & Payments

## Product Requirements Document

**Version:** 1.0
**Status:** Ready for AI-assisted development
**Application Type:** Internal web application with client portal
**Backend:** Laravel
**Frontend:** React + Inertia
**Database:** SQLite
**Authentication:** Laravel authentication
**Currency Conversion:** None
**Accounting Integration:** None
**Payment Gateway:** None
**Mobile App:** None

---

# 1. Product Overview

Build a very simple web application for managing:

```text
Clients
    ↓
Projects
    ↓
Payments
    ↓
Outstanding Balance
    ↓
Client Account Statement
```

The application's primary purpose is to answer:

> **How much has this client been charged, how much have they paid, and how much do they still owe?**

The application should be intentionally simple.

It is **not**:

* An accounting system
* An invoicing system
* A CRM
* A task management system
* A time tracking system
* A full project management platform

Projects are simply financial/project records belonging to a client.

---

# 2. Core Business Model

Each client has:

* Basic contact information
* A default currency
* Projects
* Payments
* Account balance

A project has:

* Name
* Description
* Optional link
* Amount

A payment has:

* Amount
* Currency
* Date
* Payment method
* Received/recorded by
* Optional project assignment
* Optional note

The client's account balance is calculated from the client's projects and payments.

---

# 3. Most Important Financial Rule

A payment does **not** have to belong to a project.

There are two types of payments.

## 3.1 Project Payment

A payment can be assigned to a specific project.

Example:

```text
Project A = $5,000

Payment:
$2,000
Assigned to Project A
```

The project has:

```text
Paid:        $2,000
Remaining:   $3,000
```

## 3.2 Account Payment

A payment can be unassigned.

Example:

```text
Project A = $5,000
Project B = $3,000

Total Projects = $8,000

Payment 1 = $4,000
Payment 2 = $2,000

Neither payment assigned to a project.

Total Paid = $6,000

Outstanding = $8,000 - $6,000
            = $2,000
```

This is the most important accounting rule in the application.

---

# 4. Client Account Balance

The authoritative client balance is:

```text
Total Project Amounts
-
Total Client Payments
=
Outstanding Amount
```

Where:

```text
Total Project Amounts
=
sum of all project amounts belonging to the client
```

and:

```text
Total Client Payments
=
sum of all payments belonging to the client
```

Payment/project assignment does **not** change the total client balance.

It only provides additional information about how a payment was intended to be applied.

---


# 6. Important Currency Limitation

There is **no currency conversion**.

Therefore, the system must not silently add amounts from different currencies.

Example:

```text
Client currency: USD

Projects:
$10,000 USD

Payments:
$5,000 USD
```

Balance:

```text
$5,000 USD
```

But if the client has:

```text
Project: $10,000 USD
Payment: €2,000 EUR
```

the application cannot mathematically calculate a single USD balance without conversion.

Therefore, the system must handle mixed-currency situations explicitly.

Recommended rule:

### Default behavior

A client's projects and payments should normally use the client's default currency.

If a payment is recorded in another currency, the system should show it separately and flag:

> **Multiple currencies — balance cannot be calculated across currencies.**

Do **not** invent or automatically use an exchange rate.

# 12. Payment Assignment

`project_id` is nullable.

This is deliberate.

Example:

```text
Payment #001
Client: ABC
Amount: $5,000
Project: Website
```

versus:

```text
Payment #002
Client: ABC
Amount: $5,000
Project: None
```

The second payment is an account-level payment.

---

# 13. Payment Validation

A payment assigned to a project must belong to the same client.

Invalid:

```text
Payment Client: Client A
Payment Project: Project belonging to Client B
```

The backend must reject this.

The frontend must never be trusted to enforce this relationship.

---

# 14. Payment Overpayment

The system should allow payments that exceed the current outstanding amount.

Example:

```text
Projects:
$5,000

Payments:
$6,000

Result:
Credit = $1,000
```

Do not force the user to artificially assign the extra $1,000 to a project.

The client account should show:

```text
Outstanding: $0
Credit: $1,000
```

This is preferable to showing a negative outstanding balance.

The underlying calculation remains:

```text
Net Balance = Projects - Payments
```

but the UI represents negative balance as client credit.

# 33. Dashboard Outstanding Calculation

For a client with a single currency:

```text
Project Total
=
SUM(project.amount WHERE status != cancelled)

Payment Total
=
SUM(payment.amount)

Net Balance
=
Project Total - Payment Total
```

Then:

```text
if Net Balance > 0:
    Outstanding = Net Balance
    Credit = 0

if Net Balance < 0:
    Outstanding = 0
    Credit = abs(Net Balance)

if Net Balance == 0:
    Outstanding = 0
    Credit = 0
```

---

# 34. Multi-Currency Handling

Because currency conversion is explicitly out of scope, the application should encourage currency consistency.

Recommended client setting:

```text
Default Currency: USD
```

When creating:

* Project
* Payment

the client's currency should be preselected.

The user may change it.

However, if transactions contain multiple currencies, the system should display separate currency totals with currency symbol or abbreviation.

Example:

```text
USD
Projects:  $10,000
Payments:   $7,000
Balance:    $3,000

EUR
Payments:   €1,000
```

The system must **not** combine:

```text
$3,000 + €1,000
```

into one balance.

---

# 35. Currency Warning

If a client account contains more than one currency, display:

> This account contains multiple currencies. Outstanding balances are calculated separately by currency. No currency conversion is performed.

This prevents misleading financial information.

# 51. Financial Record Deletion

Do not silently delete payments.

Recommended behavior:

* Normal users cannot permanently delete payments.
* Authorized users may void/delete according to permissions.
* The activity log records the operation.

For this simple application, a payment can remain in the database with a status:

```text
active
void
```

Then calculations only include active payments.

This is safer than physically deleting financial history.

---

# 52. Payment Status

Add:

```text
Active
Voided
```

Only active payments contribute to account balances.

---

# 53. Project Status and Balance

Cancelled projects should be excluded from the account balance.

Completed projects continue contributing to the account balance.

This means:

```text
Active      → Included
Completed   → Included
Cancelled   → Excluded
```

---

# 54. Project-Level Balance

For a project:

```text
Project Amount
-
Payments Assigned Directly To Project
=
Project Balance
```

Important:

**Unassigned account payments do not reduce the project's displayed balance.**

They only reduce the overall client outstanding amount.

This distinction must be clearly communicated in the UI.

# 55. Example — Real-World Scenario

Client:

```text
ABC Company
Default Currency: USD
```

Projects:

```text
Website       $10,000
Branding       $5,000
Hosting        $2,000
```

Total:

```text
$17,000
```

Payments:

```text
$5,000 → Website
$3,000 → Account
$2,000 → Account
```

Total payments:

```text
$10,000
```

Client outstanding:

```text
$17,000 - $10,000
= $7,000
```

Website project:

```text
$10,000 - $5,000
= $5,000
```

Branding:

```text
$5,000
```

Hosting:

```text
$2,000
```

The project balances total $12,000 because the $3,000 + $2,000 account-level payments have not been assigned to individual projects.

That is **acceptable and intentional**.

The client's authoritative balance remains:

```text
$7,000
```

# 80. Financial Rules for the AI Agent

The following rules are immutable:

### Rule 1

Client outstanding is calculated from the client's projects and payments.

### Rule 2

A payment may optionally belong to a project.

### Rule 3

An unassigned payment belongs to the client account.

### Rule 4

Unassigned payments reduce the client's overall outstanding balance.

### Rule 5

Unassigned payments do not reduce an individual project's displayed balance.

### Rule 6

Cancelled projects do not contribute to the outstanding balance.

### Rule 7

Overpayments become client credit.

### Rule 8

Money uses decimal database types.

### Rule 9

No currency conversion exists.

### Rule 10

Different currencies must never be mathematically combined.

### Rule 11

The backend is authoritative for all financial calculations.

### Rule 12

Client users can never access another client's information.

# 81. Final Data Flow

The entire application can be understood as:

```text
CLIENT
  │
  ├── PROJECT 1 ─────── Amount
  │
  ├── PROJECT 2 ─────── Amount
  │
  ├── PROJECT 3 ─────── Amount
  │
  └── PAYMENTS
        │
        ├── Payment → Project 1
        ├── Payment → Project 2
        └── Account Payment
```

Then:

```text
TOTAL PROJECT VALUE
        -
TOTAL CLIENT PAYMENTS
        =
OUTSTANDING / CREDIT
```

# 83. Product Definition

The entire product should be thought of as:

> **A simple client account ledger centered around projects and payments.**

Its core relationship is:

```text
Client
   ↓
Projects = What the client owes
   ↓
Payments = What the client has paid
   ↓
Balance = What remains
```

Everything else exists only to make that information easier to enter, understand, communicate, and export.

**The application should remain small by design.**
